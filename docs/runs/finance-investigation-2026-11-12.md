## Update after the audit (12 November 2026, later)

What changed in code, all tested with a scripted model and the real kernel, MCP server and SDK client (no spend):
- The truncation had one root cause: the final answer was free text with a 4000 token cap, so a verbose answer was cut off. The agent now ends by calling a `submit_findings` tool with a strict schema (enum pairs and classes, short rationale), allows 8000 then 16000 output tokens per turn, discards a truncated turn without executing anything from it, and returns an invalid submission to the model as a tool error so it can fix citations itself. No reconstruction step remains. `finance-resume.ts` and `finance-derive.ts` are retired.
- Paid-result replay: a served result is stored in the same transaction as the charge (`apps/api/sql/tool_results.sql`, `resultStore` in `meter.ts`). Retrying with the same idempotency key returns the stored result with `receipt.replayed: true` and `charged_minor: 0`, calls no provider, and writes no new journal rows. A refused key stays refused. Without the table applied, the old behaviour (idempotency_conflict) remains.
- Judging recovery: a job that was delivered but never decided (the process died or judging threw) resumes when the seller resubmits the same text (`deliverJob`). Not covered: a job held after one provider failed (no round 2), a crash between decision and capture, and a lost PayPal capture or payout response before it is recorded. The deliverable text is still not stored, so recovery needs the seller to resend it.
- MCP: an unauthenticated `tools/call` now returns HTTP 401 with `WWW-Authenticate`. GET and DELETE on `/mcp` return 405 (the server is stateless).
- Evaluation: 12 pairs, withheld labels, four baselines, held-out split. See `finance-eval-2026-11-12.md`.

The four-pair statements above describe the earlier recorded runs. The twelve-pair fixture uses a 20-cent bundle and two-cent lookups. Create a new `live_finance_*` database with the contract schema, roles and replay table. Use `FIXTURE_DATABASE` to point the fixture launcher to that database.

- **Recorded PayPal sandbox, sixteen-cent hold.** The twelve-pair model completed in one run after choosing five two-cent lookups (B, C, I, F, J). - **Current local fixture.** The updated finance harness exposes the free preflight to the model, sends bare UUIDs over Streamable HTTP and traces requests before dispatch. If a committed tool reply is lost, the first received answer can be a zero-charge replay. The harness records the original commitment exactly once. The explicit integration test scripted a model and PayPal responses. With a 20-cent fixture authorization, the model stub saw the bundle as affordable, bought one lookup, received a cap refusal on the bundle, then bought two more lookups. It returned three evidence-backed findings and nine abstentions. The database matched all receipts, three balanced commit groups, a refusal without a posting, and three allocations totaling six cents. A lost fixture capture response reconciled by GET with one capture POST. A separate fixture lease bought the bundle for 20 cents and returned all 12 evidence records.

The receipt-to-journal verifier now reads only. It accepts recorded digest-form keys and current bare UUIDs, checks the actual lease and postings, and links captures to their allocations. Run it from `apps/api`:


The optional `--paypal-sandbox-read` flag uses sandbox credentials to fetch the authorization and completed captures independently. The file includes allowlisted fields only. Settlement and reconcile are separate operator actions. Neither happens during trace verification.
