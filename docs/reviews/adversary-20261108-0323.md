# Adversarial review: Experience and Rails

Date: 2026-11-08 IST
Scope: `/lease/plate`, `/journal`, `/proof`, `/story`, `/escrow`, `/approve`, `/lease/hold`, `/lease/void`; current `apps/api` and `packages/paypal` source.

## Ranked findings

### 1. blocker: The default API cannot perform any paid operation

**Evidence.** `createApp()` only installs the two read handlers and then binds `unavailableKernelMeter` to MCP. Every other OpenAPI operation lacks a handler, so `createRoutes()` returns 503. Even the registered MCP tools always return `metering_unavailable`. The PayPal client exists but is not wired to create/authorize/capture/void/payout or webhook routes. That leaves the product’s central flow unavailable in the default app composition.

**Reproduction.** `pnpm --filter @pashadhara/api test` passes the existing `production meter fails closed until nonce binding is atomic` test. Source confirms `apps/api/src/app.ts:13-15` passes the fail-closed meter; `apps/api/src/routes.ts:78` returns 503 for absent handlers; `apps/api/src/mcp.ts:14-15` unconditionally returns `metering_unavailable`.

**Fix.** Wire the authenticated HTTP handlers to kernel and PayPal operations, including intent-before-send and read-before-retry, and only advertise paid MCP tools when their real meter is available. Until then describe the deployed app as a fail-closed scaffold, not an operational payment gateway.

### 2. major: Reconciliation crashes for the supported multi-capture authorization flow

**Evidence.** `compareJournal()` joins all captures on an authorization and requires exactly one joined row. PASHADHARA’s sandbox evidence contains 12 successful partial captures against one authorization, and the product explicitly supports this flow. Thus a real lease with two captures causes reconciliation to throw before it can compare data. Its current connected integration fixture creates only one capture and misses the supported shape.

**Reproduction.** From `apps/api`:

```powershell
pnpm exec tsx -e "import {compareJournal} from './src/compare-journal.ts'; const db={transaction:async(_lease,work)=>work({query:async()=>({rows:[{},{}]})})}; compareJournal(db,'fixture-lease',{id:'auth',status:'PARTIALLY_CAPTURED'},{id:'capture-1',status:'COMPLETED'},'fixture').catch(e=>console.log(e.message));"
```

Output:

```text
Expected exactly one authorization and capture
```

Location: `apps/api/src/compare-journal.ts:14-20`.

**Fix.** Select the local capture by PayPal capture id (or compare a complete capture set), compare the authorization once, and return explicit missing/extra-row differences instead of throwing. Add a two-capture integration case.

### 3. minor: Requested 390 px and full accessibility checks remain unverified

**Evidence.** Edge’s accessibility tree for `/lease/plate` exposes the skip link, named navigation, H1, chart image name, and labelled range slider. I found no unnamed interactive control on that route. A 390 px automated pass could not be completed: local Playwright reports that its configured Chromium executable does not exist. I did not treat earlier status screenshots as evidence for these current routes.

**Reproduction.** `pnpm --filter @pashadhara/web exec playwright --version` is not needed to see the blocker; the attempted headless route sweep failed at `chromium.launch()` with `Executable doesn't exist at ...chrome-headless-shell...` and advised `npx playwright install`. No browser binary was installed as part of this review.

**Fix.** Run the eight routes at a 390 px viewport in the supported Edge/browser test setup and record overflow, visible text sizing, contrast, keyboard focus, and screen-reader control names. No accessibility defect was established from the checks I could perform.
